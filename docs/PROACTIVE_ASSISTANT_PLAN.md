# Proactive Assistant: MVP plan

Status: built in one pass on 2026-11-05 (the phase handoffs in section 15 were not used). Live verification items are listed in section 15.
Branch: `feat/tanstack-start`. Target: a pilot with 2 to 3 real users on Google Chat and the in-app AI chat.

## 1. What the MVP does

1. **Checks in on its own.** Once per working day, the assistant messages each opted-in person about
   the work that needs their word: stale or due-soon commitments and dependencies they owe. Google Chat
   DM if linked, and always in the in-app AI chat.
2. **Updates work from the reply.** "1 is 70%, 3h left. 2 is done" updates item 1 immediately and asks
   to confirm item 2's completion. Routine numbers apply automatically. Anything consequential waits
   for a yes.
3. **Clears up ambiguity.** When a reply is vague ("going well", "almost done", "will be late"), it asks
   one short, specific question. That's at most two rounds, then it saves what was clear and stops.
4. **Speaks one format in two places.** Messages are written once in a small markdown subset and rendered
   correctly in Google Chat (Chat's own syntax) and in the app (React elements, never raw HTML).
5. **Keeps the files and links people send with an update.** A screenshot, document or link sent with a reply is
   recorded against the commitment it belongs to (and so its project). It's listed on the commitment, on the
   project, and on a workspace "Files & links" page sorted by date and filtered by team, project, and person.
   TeamPulse stores **references only** (Google Chat's own attachment link, the Drive link, or the URL). It never
   copies file bytes into storage of its own.

Manager update requests (the Update center) feed into the same reply handling, so a reply to a manager
also updates the work.

### Out of scope for the MVP

- Free-form agent decisions: assigning work, changing priority, creating commitments for others.
- Multiple check-ins a day, per-person times or timezones (one org timezone is enough for 2 to 3 users).
- Follow-up reminders when someone does not reply. Silence stays visible as "Update needed"; we never
  infer progress from it.
- Chat cards or buttons. Text only: yes/no replies are enough.
- Languages other than English.
- File upload inside the TeamPulse app (there is no file storage). In the app, people paste links; files come
  in through Google Chat.
- Thumbnails generated by TeamPulse, virus scanning, and editing or deleting someone else's file.

### New table `check_ins`

|---|---|---|
| id | int pk | |

| kind | str(20) | `daily` or `request` (a manager's UpdateRequest) |

## 5. Outbound: the daily check-in

`services/proactive.py`

```python
def run_check_ins(db) -> int:
    """Called every tick. Sends at most one daily check-in per person per day."""
```

1. Return early unless `PROACTIVE_ENABLED`, it is a weekday, and local time (`ORG_TIMEZONE`) is at or after
   `CHECKIN_HOUR` and before 18:00.
2. Expire stale check-ins: `Open`/`Clarifying`/`Confirming` past `expires_at` become `Expired`, and their
   unconfirmed `AgentAction`s become `Dismissed`.
3. For each active employee with `proactive_checkins` true, not paused, and no `daily` check-in for today:
   `items = select_items(db, person)`. Skip the person if it's empty (no message is good news).
4. Create the `CheckIn` (catch `IntegrityError` and skip: someone else won the race), write the message as an
   assistant `Conversation` row (`agent='Check-in agent'`), add an in-app notification, and call
   `google_chat.queue_message(..., check_in_id=...)` if linked.

`select_items(db, person)` picks, in this order, until `CHECKIN_MAX_ITEMS`:

1. Owned active work that is overdue, or due within 1 business day, and not confirmed in the last 24h.
2. Open dependencies the person owes (`Dependency.owner_id`) that are overdue or due within 1 business day.
3. Owned active work whose confirmation is stale (>36h, the same rule as `work_health`).

Skip `Completed` work and archived projects. It reuses `latest_commitment`, `today`, `business_day`.

The existing `run_workflows` "due" in-app notifications stay as they are; the check-in is the Chat-facing
version. Do not add more notification rules.

### Message template (canonical markdown subset, see 8)

```
Morning, Priya. A quick check on 3 things:

1. **Atlas review deck**: 40%, due today
2. **Pilot region criteria**: 70%, due Fri 7 Nov
3. **Schema review for Raj** (Raj is waiting): due tomorrow

Reply in your own words, for example `1 is 80%, 2h left. 3 is done`.
Say `pause` to skip check-ins until tomorrow.
```

Keep it under about 600 characters. Titles are truncated to 60 characters. Dates use a short, friendly form
(`today`, `tomorrow`, `Fri 7 Nov`).

### Manager requests become check-ins too

In `create_requests` (`services/coordination.py`), after a request is delivered, create a `CheckIn(kind='request',
update_request_id=...)`. Its items are the recipient's active owned work, or just `request.work_item_id` if set.
The DM text stays the existing one from `GoogleChatChannel.prepare`, plus the numbered item list. The reply
goes through the same handler (6), and the handler also calls `reply_to_request` so the manager sees the
answer in the Update center.

## 6. Inbound: one router for both channels

`services/proactive.py`

```python
async def handle_inbound(db, employee, text, channel, request_id) -> dict:
    """Every message from a person, from Google Chat or the in-app chat, goes through here first.
    Returns {'reply': str (markdown subset), 'action': ...} in the same shape converse() returns."""
```

Order of checks:

1. **Commands** (exact, case-insensitive, trimmed): `pause` sets `checkins_paused_until` to tomorrow;
   `resume`; `undo` (see 7.4); `help`.
2. **A pending confirmation** on the newest open check-in (`status='Confirming'`): a yes-like answer (`yes`, `y`,
   `confirm`, `correct`, `ok`, `👍`) applies its actions; a no-like answer (`no`, `n`, `cancel`, `wrong`) dismisses them.
   Anything else goes through extraction again (the person corrected themselves).
3. **An open check-in** (`Open` or `Clarifying`, not expired, newest first): unless the message is clearly a new
   command (`coordination_intent(...)` returns something, or it starts with `plan:`), it is a reply:
   `checkin_reply.handle(db, employee, check_in, text)`.
4. Otherwise: the existing `converse(...)` (normal assistant).

Wire it in two places:

- `api/routes/integrations.py`: replace the `pending = db.scalar(select(UpdateRequest)...)` branch and the
  `converse` call with `handle_inbound(..., channel='google_chat')`. Keep `MessageReceipt` dedupe exactly as it is.
  Convert the reply with `formatting.to_google_chat()` before `_reply(...)`.
- The in-app message endpoint (`api/routes/assistant.py`, which calls `converse`): call `handle_inbound(...,
  channel='in_app')` instead. The reply stays canonical markdown; the frontend renders it.

Every turn is stored as `Conversation` rows (user + assistant), so the in-app chat shows Chat-originated check-in
threads too. That's one history across channels.

## 7. Understanding a reply: `services/checkin_reply.py`

The model only **extracts**. Code **decides** and **speaks**. Reply text comes from templates, never from the model.

### 7.1 Extraction

```python
class ItemUpdate(BaseModel):
    n: int                                   # item number from the check-in
    progress: int | None = Field(None, ge=0, le=100)
    remaining_hours: float | None = Field(None, ge=0, le=1000)
    status: Literal['In Progress', 'Completed', 'Blocked'] | None = None
    new_due_date: date | None = None
    reason: str | None = Field(None, max_length=500)       # why a date moved / what blocks
    blocker_person: str | None = Field(None, max_length=120)
    blocker_what: str | None = Field(None, max_length=200)
    evidence: str = Field(max_length=300)    # the exact words in the message this came from

class Extraction(BaseModel):
    is_reply: bool                           # false: the person is talking about something else
    updates: list[ItemUpdate] = []
    ambiguity: Literal['which_item', 'vague_progress', 'hedged_completion',
                       'date_without_date', 'slip_without_reason', 'blocker_without_owner', 'none'] = 'none'
    ambiguity_n: int | None = None
```

- **LLM path** (when `provider_configured()`): the same client as `provider_interpret`, `response_format=json_object`,
  temperature 0, 20s timeout. The system prompt gets: today's date, the numbered items (n, title, status, progress,
  remaining hours, due date), the last 6 turns of *this* check-in thread, and these rules: "Extract only what the
  person explicitly said. Never infer completion from tone. 'Almost done' is not Completed. If the item is unclear
  and there is more than one, set ambiguity=which_item. Copy the words you relied on into evidence."
- **Deterministic path** (no provider, or the LLM fails): reuse the regexes from `offline_interpret` and
  `reply_to_request` (percent, `N hours left`, `done|finished|completed`, the hedges `almost|nearly|not yet`, and
  ISO dates), plus item addressing `^\s*(\d)\s*[:.)-]|\bitem\s*(\d)\b|#(\d)`, and title-word matching. With one item,
  every number belongs to it.

### 7.2 Validation (always, on both paths)

Drop any update that fails a check. If all are dropped, treat the reply as `vague_progress`.

- `n` exists in the check-in's items, and the person still owns that work (`owner_id`) or dependency.
- Each number in `progress` / `remaining_hours` appears literally in the message text.
- `Completed` requires a completion word in `evidence`, and no hedge word in the message near it.
- `new_due_date` is on or after today and parses.
- `evidence` is a substring of the message (case-insensitive, after whitespace collapse). This is the cheapest
  defence against a hallucinated update.

### 7.3 Decision policy

| Change | What happens |
|---|---|
| progress, remaining hours, status `In Progress`, a note | **applied now** (auto) |
| status `Completed` | proposed, waits for yes |
| new due date | needs a reason; then proposed, waits for yes |
| blocked / waiting on someone | proposed as a dependency (existing `dependency` proposal kind), waits for yes |
| anything on work the person doesn't own | never |

- Auto changes go through `patch_work(...)` with `note='From check-in reply: "<evidence>"'`. Store each as an
  `AgentAction(source='checkin', status='Applied', applied_at=now, base_snapshot=snapshot(before))` for undo. Audit
  message: `Updated by the assistant from {Name}'s check-in reply (Google Chat)`.
- Changes that need a yes become `AgentAction(status='Proposed', source='checkin', check_in_id=...)`. The check-in moves
  to `Confirming` with `pending_json={'type':'confirm','action_ids':[...]}`. In-app, these appear as the existing
  `ProposalCard` (Confirm / Dismiss). In Chat, a yes/no reply resolves them. Both paths call the same `apply_proposal`.
- On a confirmed date slip or new blocker, notify the person's manager (in-app notification, plus a Chat DM if
  linked): `Priya moved **Atlas review deck** to Mon 10 Nov: waiting on client data.`
- When every item is answered (updated, confirmed or explicitly skipped), the check-in becomes `Done`.

`agent_auto_updates` keeps its current meaning for the free-form assistant. Check-in replies auto-apply routine
numbers for everyone opted in to check-ins, because the person answered a direct question about that item. Undo
is the safety net.

### 7.4 Undo

`undo` reverts the person's most recent `Applied` check-in actions from the last `UNDO_WINDOW_MINUTES`. It only
works if the work still matches what the action wrote: compare `snapshot(work)` to the after-state. If the work has
moved on, it says so and changes nothing. A revert is a normal `patch_work` with the `base_snapshot` values and the
note `Undone from check-in`.

### 7.5 Ambiguity: one question at a time

Each `ambiguity` value maps to one templated question. Ask it, increment `clarify_rounds`, and set status `Clarifying`.
Anything already clear in the same message is still applied first, and the reply says so.

| ambiguity | question |
|---|---|
| which_item | `Which one is that about? Reply with its number: 1. Atlas review deck, 2. Pilot region criteria` |
| vague_progress | `Roughly how far along is **Atlas review deck**? A percent or hours left is enough, like "60%, 3h left".` |
| hedged_completion | `I'll keep **Atlas review deck** open. What's left, and about how many hours?` |
| date_without_date | `What date should **Atlas review deck** move to?` |
| slip_without_reason | `Got it, Mon 10 Nov. What changed? One line is fine; your manager sees it with the new date.` |
| blocker_without_owner | `Who or what is **Atlas review deck** waiting on?` |

After 2 rounds: save what is clear, close the check-in as `Done`, and reply `Thanks, I saved what I could. Anything
else, update it in TeamPulse: <link>`. Never loop.

If `is_reply` is false, hand the message to `converse` (the normal assistant). The check-in stays open.

### 7.6 Reply templates (after a turn)

```
Saved:
- **Atlas review deck**: 80%, 2h left
- **Pilot region criteria**: 75%

Mark **Schema review for Raj** as done? Reply `yes` or `no`.
```

If a turn changed nothing, don't invent a summary; ask the question (7.5) instead.
Every applied summary ends with a short `Say undo to reverse this.` while undo is still available.

## 8. One format, two renderers

### 8.1 The canonical subset (used by every template and allowed in model output)

- Paragraphs separated by a blank line; single newlines kept.
- `**bold**`, `_italic_`, `` `code` ``.
- Bullets: lines starting with `- `. Numbered lists: lines starting with `1. ` and so on.
- Links: `[text](https://...)`, https only.
- Nothing else: no headings, tables, images, HTML, or nested lists.

### 8.2 `services/formatting.py`

```python
def sanitize(md: str) -> str:        # strip anything outside the subset (headings -> bold line, tables -> lines, HTML tags removed)
def to_google_chat(md: str) -> str:  # **x** -> *x*;  _x_ stays;  `x` stays;  "- " -> "• ";  "1. " stays;
                                     # [t](u) -> <u|t>;  escape a literal * or _ that is not formatting;  cap 4000 chars
def to_plain(md: str) -> str:        # for notifications: markers removed, links -> "text (url)"
```

Google Chat's text syntax is `*bold*`, `_italic_`, `~strike~`, `` `code` ``, and `<url|label>` for links. It has no
markdown headings, so bold is the only emphasis that carries. Put both renderings of the 7.6 example in the
module docstring as the contract.

Apply `sanitize` to every assistant reply before storing it, including `converse()` replies from the LLM, so the
in-app history only ever holds the subset. Apply `to_google_chat` at the Chat edge only: in `_reply()` and in the
outbox text for check-ins.

### 8.3 `frontend/src/components/ui/RichText.tsx`

- Parses the same subset into React elements: `<p>`, `<ul><li>`, `<ol><li>`, `<strong>`, `<em>`, `<code>`, `<a>`.
- Builds the element tree directly. **Never `dangerouslySetInnerHTML`**; user text stays text.
- Links only for `https:` URLs, with `target="_blank" rel="noopener noreferrer"`. Anything else renders as plain text.
- No new dependency: a hand-written parser of about 80 lines, for this small grammar only.
- Replace `<p>{m.message}</p>` at `ChatWorkspace.tsx:414` with `<RichText text={m.message} />`. Use it for
  check-in messages, proposal replies and Update-center prompts. User messages stay plain text.
- Styles in `chat.css`: tight list spacing, `code` in Geist Mono on a tinted background, links in the brand colour.

## 9. Files and links sent with updates

### 9.1 The Google Chat link is not a public CDN link (read this first)

When someone sends a file to the Chat app, the event carries `message.attachment[]`, each with `contentName`,
`contentType`, `source` (`UPLOADED_CONTENT` or `DRIVE_FILE`), `downloadUri`, `thumbnailUri`, and either
`attachmentDataRef.resourceName` (uploads) or `driveDataRef.driveFileId` (Drive files).

- `downloadUri` and `thumbnailUri` open only for someone signed in to Google **who is a member of that DM space**.
  The DM is between the employee and the TeamPulse app, so the manager is not a member. Pasting the raw link into
  the manager's view gives them "no access".
- A Drive file link opens for whoever the file is shared with in Drive. That is the owner's choice, not ours.

**Decided (2026-11-05):** the user tested it, and the copied image address stops working after about a day.
**Use the streaming path below.** Save the attachment's `resourceName` and fetch the file from the Chat API
each time someone opens it. The check below is kept for reference only.

**Check this first (step 0 of section 9).** In the Chat web UI, the image address ("Copy image address", usually
`lh3.googleusercontent.com/...` or similar) did open in an incognito window: it's a link that works for anyone who
has it. That is not necessarily the same URL as the API's `downloadUri`/`thumbnailUri`, and links like this
often expire. Before building 9.3, log one real event's `attachment[]` (field names and hosts only, never
log the full URL), then open its `downloadUri` and `thumbnailUri` in incognito, both straight away and again
after 24 hours.

- **If they open without sign-in and still work after 24h:** store that URL and open it directly (302), as for
  links. Drop the streaming path. This is the simplest option and matches the original intent. Treat the URL as a
  secret: show it only to people who can see the commitment, and never put it in a Chat message to anyone else.
- **If they need sign-in or expire:** use the streaming path below.

Otherwise TeamPulse saves the link **and** the reference, and opens files through itself. Nothing is copied into storage:

- **Uploads (`chat_upload`):** the manager clicks *Open* and gets `GET /api/attachments/{id}/open`. The backend
  checks they may see that commitment, then streams the bytes from the Chat API's media download endpoint
  (`GET https://chat.googleapis.com/v1/media/{resourceName}?alt=media`) with the app's service-account token,
  straight through to the browser. Nothing is written to disk or the database. Keep `downloadUri` as a fallback
  link for the sender. **Verify during build** that the app's `chat.bot` credentials can download an attachment from
  a DM it received. If they can't, ship links-only and show the uploader a note: "Share it from Drive so your
  manager can open it."
- **Drive files (`drive_file`):** store and show the Drive link. When the manager can't open it, Drive itself asks
  for access. TeamPulse does not change Drive sharing.
- **Links in the text (`link`):** every `https://` URL in an update reply, from Chat or the in-app chat, is stored
  as-is.

### 9.2 Capture

`services/attachments.py`

```python
def capture(db, employee, *, text, chat_attachments, chat_message, work_item_ids, check_in=None, request=None) -> list[Attachment]:
```

- Called by `checkin_reply.handle` (and by the manager-request path) after the turn has decided which items it is
  about. `chat_attachments` is the raw `message.attachment` list (empty for the in-app chat).
- **Which commitment:**
  - The turn updated or named exactly one item: attach to that item.
  - It named several items: attach to each item named in the same sentence as the file or link. If that can't
    be told apart, attach to every item the turn updated.
  - A file arrives with no text and the check-in has one item: attach to it.
  - It can't be decided (a file alone, several open items): ask the one question
    `Which item is this file for? Reply with its number: 1. ..., 2. ...` (a new ambiguity type, `which_item_for_file`).
    Keep the raw attachment JSON in `pending_json` until it is answered. An unanswered file expires with the check-in.
  - With no open check-in and no manager request: the router (6) attaches it to the work item selected in the
    in-app chat. In Chat, ask "Which of your commitments is this for?" and list up to 5 active items.
- **Media-only messages:** today the Chat route ignores messages shorter than 3 characters. Let a message with
  attachments through even when its text is empty.
- Store `note` as the reply text (truncated), so the list shows what the file was evidence of.
- Reply template addition: `Attached to **Atlas review deck**: screenshot.png, figma.com/file/…`.
- The audit event on the work item: `Priya attached screenshot.png (from Google Chat)`.
- If the reply answered a manager request, the Update center response shows the attachments under the reply text.

### 9.3 API

```
GET /api/attachments?project_id=&team_id=&person_id=&work_item_id=&kind=&before=<iso datetime>&limit=50
GET /api/attachments/{id}/open
```

- **List:** only attachments whose `work_item_id` is in `visible_work(db, user)`, the same rule as everything
  else. `team_id` filters on the sender's team (`Employee.team_id`). `person_id` filters on the sender and must be
  someone the viewer can see. Newest first, with keyset pagination on `(created_at, id)` via `before`.
  The response includes the sender's name, the work title, the project name and colour, and `can_open`.
- **Open:** checks the same visibility, then:
  - `link` and `drive_file`: `302` to the stored https URL.
  - `chat_upload`: stream from the Chat media endpoint. Response headers `Content-Disposition: attachment;
    filename="<sanitized>"`, `X-Content-Type-Options: nosniff`, and `Content-Security-Policy: sandbox`. Display
    inline only for `image/png|jpeg|gif|webp` and `application/pdf`. Everything else, especially HTML and SVG,
    downloads. User files must never run on the TeamPulse origin.
  - Use a 30s upstream timeout and a 25 MB cap. On failure, return `502` with "Google Chat did not return this
    file. Ask the sender to share it again."
  - The open endpoint must be reached through the app (signed-in session), never through the public ngrok host.
    `PUBLIC_PATHS` stays as it is.

### 9.4 Where people see them

All three views use one shared `AttachmentList` component. Each row is a container with an icon by type (image,
PDF, document, link), the file name as plain text, the sender's avatar and name, the commitment title (opens
the commitment), the project chip, and the date and time. "Open" opens the open endpoint in a new tab. Images show
a small thumbnail through the open endpoint (inline image types only). Rows are grouped under date headings
(`Today`, `Yesterday`, `Mon 3 Nov`, ...), newest first.

1. **Commitment:** a new "Files & links" tab in `WorkDetail` (next to Update, Dependencies, History), filtered
   by `work_item_id`.
2. **Project:** a new "Files & links" tab on the project page (`PROJECT_TABS`), filtered by `project_id`, with a
   person filter (project members).
3. **Workspace page:** "Files & links" in the sidebar (route `/files`), everything the viewer can see.
   Filters: team, project, project member (person), and type (files or links). Filters live in the URL search
   params, like the other pages. Use "Load more" for pagination.

Empty states: "No files or links yet. When someone sends one with an update, it shows up here."
Tabs use the existing `TabPanel`, so they get the same transitions.

## 11. Production for a 2 to 3 person pilot

- **One backend process** (`uvicorn` with no `--workers`). The tick runs in-process. The unique constraint makes
  duplicate check-ins impossible anyway.
- **A stable public URL** for Chat events: keep the reserved ngrok domain, with the backend started on login
  (a Windows scheduled task: `uvicorn` plus `ngrok`). It must survive reboots; otherwise check-ins fire but replies
  never arrive.
- **Kill switch:** `PROACTIVE_ENABLED=false` stops all outbound messages within one tick.
- **Privacy:** never log message text or model output (the existing Chat rule). Log ids, counts and timings only.
- **LLM:** Groq JSON mode with temperature 0 and a 20s timeout. On any failure, fall back to the deterministic path.
  The validation in 7.2 runs either way.
- **Every automatic write** carries an audit event and a `Conversation` trail. Undo covers the last two hours.
- **Back up** Postgres (`cli/backup.py`) before the first live day.
- **Files:** no bytes are stored, so there's no storage quota. A file stays openable only while Google keeps it in
  the DM. If the employee deletes the message, the row stays but Open returns the 502 message.

## 13. Acceptance (what "done" looks like)

- At 10:00 IST on a weekday, a pilot user with stale work gets exactly one DM. A restart at 10:01 sends nothing new.
- "1 is 80%, 2h left" changes item 1's progress and hours. The audit shows it came from the check-in. `undo` restores it.
- "2 is done" does not complete anything until `yes`. `no` leaves it untouched.
- "going fine" gets the vague-progress question. A second vague answer gets one more question. A third ends politely.
- "will be late" asks for a date, then a reason. After `yes`, the manager is told the new date and the reason.
- The same reply text renders bold, bullets and links correctly in Google Chat and in the app, and a message
  containing `<script>` shows as literal text in the app.
- With `PROACTIVE_ENABLED=false`, nothing is sent and the inbound router still works for manager requests.
- A screenshot sent in Chat with "1 is 90%" appears in item 1's Files & links tab, in its project's tab and on
  `/files`. The manager can open it from TeamPulse without being in the DM. The same event delivered twice
  stores one row.
- A file sent alone, with two open items, gets "Which item is this file for?", and the answer attaches it there.
- A link pasted in the in-app chat while a commitment is selected is stored against that commitment.
- `/files` filtered by team, then by person, shows only what the viewer may see, newest first, grouped by day.
- An uploaded `.html` or `.svg` file downloads instead of rendering.

## 14. Decisions made here (change them before building if you disagree)

1. Routine numbers from a check-in reply apply without confirmation. Completion, date moves and blockers wait for a yes.
2. One daily check-in, weekdays at 10:00 in one org timezone. No reminders on silence.
3. The model extracts and code writes the replies (templates), so wording stays predictable and checkable.
4. Undo window: 2 hours.
5. Pilot users are opted in by default. Each person can turn it off or pause it.
6. Files are opened through TeamPulse, which streams them from Google Chat on demand, because Chat's own links
   only open for members of the DM. Nothing is stored. Drive files and plain links open directly.
7. A file with no clear target makes the assistant ask which item it belongs to; it never guesses.
8. No file upload inside the app for the MVP. Links only there.
